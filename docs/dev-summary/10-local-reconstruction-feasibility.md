# 开发总结 10：阶段 8 —— 局部重建与融合可行性验证

> 指南阶段 8 验收："至少能完成区域选择和任务创建。如果实现局部更新，必须证明目标区域发生变化且非目标区域没有明显破坏。如果无法完成，应明确说明技术限制和后续路线，不得伪称完整功能已实现。"
> 本轮交付：**区域选择原型（应用内） + 区域提取任务原型 + 区域级可行性实验 + 诚实的可行性结论**。局部重建（为新照片重算区域几何）**未完整实现**，本文给出原因与工程路线。

## 1. 应用内原型（已实现）

| 组件 | 内容 |
| --- | --- |
| 数据库 | `model_regions` 表（Alembic 迁移 `e22a01f0fd1e`）：模型坐标包围盒 + 框选时相机参数 |
| 查看器 | `ModelViewer.vue` 框选模式：拖拽矩形 → 9 点射线求交 → 模型坐标包围盒 → 3D 橙色高亮（Box3Helper） |
| API | `POST/GET /api/v1/models/{id}/regions`（保存/列出选区）；`POST /models/{id}/local-update`（创建区域提取任务，入队异步执行） |
| Worker | `pipeline_mode=local_update`：裁剪目标模型到选区 → 登记 `stage_origin=LOCAL_REGION` 模型 + `region_report.json` |
| 测试 | 2 项 pytest（正常流 + 非法包围盒拒绝）；前端 `npm run build` 通过 |

**诚实边界**：原型任务做的是**区域提取**（裁剪导出），不是局部重建——模型列表与任务清单中的说明文字均明确标注"区域提取（非局部重建）"。

## 2. 区域级可行性实验（真实数据）

方法：以源相机 P1180165 视野中央 40% 反投影为"框选区域"（模拟用户框选），对比同一区域在 2000px（任务 #7）与 3000px（任务 #11）重建下的指标（`scripts/region_feasibility.py`）：

| 指标（框选区域内） | 2000px | 3000px | 变化 |
| --- | ---: | ---: | --- |
| 点数 | 120,862 | 334,654 | **+177%** |
| 点密度（NN 间距中位） | 2.34mm | 1.64mm | **+43%** |
| 区域内网格面 | 51,223 | 81,231 | **+59%** |
| 区域外点数 | 1,859,035 | 3,413,749 | 同比例全局增长 |

能看见该区域的相机：40 张中 **16 张**（列表已生成，存于 region_feasibility.json）——这是局部更新调度（只需重跑这 16 张的深度图）的输入。

## 3. 技术限制与结论

1. **COLMAP 工作区是全局的**：`patch_match_stereo`/`stereo_fusion` 以整个 workspace 为单位，做"只重算 16 张相机"需要构建子模型（过滤 images.bin/points3D.bin 并保持一致性）或依赖已有深度图缓存 + 增量融合。深度图缓存复用在本管线已有实证（第一阶段断点重入时旧深度图被复用），因此**增量路线可行但需开发**。
2. **边界处理**：任何区域裁剪都会产生开放边界（本实验的 crop 同理）；若未来做局部更新，边界处的网格缝合需要额外的融合带（overlap band ≥ 2×depth 精度）。
3. **成本对比**：全局 3000px 重跑 40 张双卡仅 29 分钟——对 40–100 张规模，**全局重跑比局部更新的工程复杂度更划算**；局部更新的价值在数百张以上或"只允许动一个立面"的场景。
4. **结论**：区域选择与任务创建原型 ✅；局部重建未实现——原因（工作区全局性 + 边界缝合）、量化收益（区域内密度可 +43%）与后续路线（深度图缓存 + 增量融合 + 子模型构建）如上，未伪称完整功能。

## 4. 后续路线（如立项）

1. 子模型构建：按可见性筛选相机 → 导出子 sparse model → 子工作区独立稠密重建；
2. 深度图缓存增量融合：保留旧深度图，仅对新相机 patchmatch → `stereo_fusion` 融合 → 区域裁剪替换旧网格对应区域；
3. 边界融合带与无缝贴图（复用 COLMAP texturer 的视角选择）；
4. 与阶段 7 的"追加照片版本更新"集成：追加照片时若只影响某区域，走局部流程并发布新版本。
