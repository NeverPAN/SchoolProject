# 建议补测：性能、版本更新与最终验收

这份清单供组员在集群空闲时复测。现有结果见 [GPU 与分辨率实验报告](11-gpu-resolution-benchmark.md)及[原始证据](../gpu-benchmark-evidence/)。本页的建议与预计时长不是新实测结果。

## 1. 先测哪一组

| 顺序 | 补测 | 怎样选对照 | 预留计算时间（仅排期） |
| --- | --- | --- | --- |
| 1 | **Bridge 100 张 · 双卡 2000 px** | 先补矩阵空格；历史参照为隔离服务项目 2 的任务 #6（单卡 2000 px，83.91 分钟）。要发表严格同版本结论，再在同一测试版本上重跑单卡 2000 px，一并比较。任务 #13 同时变了卡数和分辨率，不能当纯卡数对照 | 双卡一轮约 51–57 分；重跑单卡参考 84 分 |
| 2 | **South Building 40 张 · 单卡 3000 px** | 对照 #11（双卡 3000 px，29.17 分），必要时同版本重跑双卡组；用原 40 张快照，不用后来已追加至 50 张的项目图片集合 | 单卡一轮约 46–53 分 |
| 3 | **Bridge 100 张 · 单卡 3000 px** | 对照 #13（双卡 3000 px，75.89 分）；如果时间不足，最后补这格，仍标明估算 | 单卡一轮约 113–129 分 |
| 4 | 重复关键配置 | 优先重复 Bridge 2000 px 单/双卡；同配置尽量各做 3 次，再扩展到 3000 px。交错顺序、串行执行，报告均值、范围、标准差与实际次数，保留慢跑和失败记录 | 按每轮分开预约，不同时占用同卡跑两个对照组 |

空闲窗口仅够一轮时，先跑第 1 项并保留原始证据。只能跑短实验时，可用同一个去畸变工作区作为只读种子，各自复制到**没有旧深度图、法线图或检查点**的新目录，仅对照 PatchMatch；所得结论只适用于稠密阶段，不能代替端到端结果。

## 2. 怎么选版本和配置

1. **区分代码版本、任务和模型。** 正式 A/B 两边固定同一 Git 提交、同一容器与引擎。若复现上一轮优化，可用包含双卡适配的已知提交 `7f8832b`；若要验收最终交付版，选届时准备交付的提交，两边都在该提交重跑。记录 `git rev-parse HEAD`、工作区是否干净、引擎版本与二进制哈希。`baseline-pre-opt-20261120` 是回滚和历史复现点，不应作为同版本 A/B 的单卡端；`#6`、`#11`、`#13` 是历史任务 ID，不是 Git 版本。不要切换正在运行服务的工作树；部署参照[部署手册](../deployment.md)。
2. **锁定输入。** 从对应历史任务的 `input_manifest` 恢复原文件，核验逐张 SHA-256、文件名及顺序，并与[历史任务输入摘要](../gpu-benchmark-evidence/task-metrics.json)对照。Bridge 固定既有 100 张，不重新取样或转码；South 固定原 40 张。新项目的数据库图片 ID 等元数据可能变化，因此同时保存跨项目可核验的逐图内容清单，不只比较一个任务摘要。
3. **用隔离服务提交新任务。** 使用独立 SQLite、Redis 队列、存储和 scratch；单 Worker 串行。不要在正式演示项目里恢复旧任务做计时。按下表设置 Worker，切组前等当前任务结束，再切换配置；申请授权的 GPU 资源，不改宿主配置、不开放端口。记录 `CUDA_VISIBLE_DEVICES` 与物理卡 UUID 的对应关系；GPU 索引是进程内可见设备索引。

| 变量 | 单卡 | 双卡 |
| --- | --- | --- |
| `RECON_USE_GPU` | `1` | `1` |
| `COLMAP_GPU_INDEX` | `0` | `0,1`，启动前确认进程能看到两卡 |
| `COLMAP_DENSE_MAX_IMAGE_SIZE` | 按本轮填 `2000` 或 `3000` | 同分辨率卡数对照时与单卡相同 |

其他条件固定：`standard`、`exhaustive`、稠密和网格开启、Poisson depth 10 / trim 10 / 4 线程、同一 COLMAP 3.13.0 CUDA 和 4.2.1 CPU 贴图器、同样的图集规则。用阶段日志和 `job_manifest.json` 核对**实际生效**参数；用设备和进程采样核对双卡确实工作，不能只看环境变量。启动前记录其他进程占用；环境不一致时注明，不混进严格对照。

## 3. 每轮怎么记录

| 类别 | 必存内容 |
| --- | --- |
| 实验标识 | 场景、组别、重复序号、Git 提交、隔离环境、任务 ID、模型 ID、日期/时区、操作者、状态或失败原因 |
| 输入与环境 | 图片数、总字节、尺寸范围、按顺序的图片名和哈希；配置摘要、引擎版本/哈希、GPU UUID、驱动、CPU/RAM/磁盘、并发负载、是否使用缓存 |
| 耗时 | 提交、领取、完成时间戳；分别算排队时间和任务墙钟（领取至终态，不含上传下载）；保留各阶段起止时间及日志；失败轮次单列 |
| 资源 | 从提交前采集空闲基线到终态：主机 CPU、任务进程 CPU/RSS、两卡利用率/显存、工作区与输出大小、磁盘可用空间。注明采样间隔、起止范围、设备级和进程级区别；最大采样值不称瞬时峰值 |
| 质量与产物 | 注册数、重投影误差、融合点数（过滤前后分开）、面数、贴图面率、GLB 字节数、朝向/降级、SHA-256；同场景固定同一组源照片、评测分辨率和点遮罩口径，记录投影覆盖/支撑及同视角截图。若有参考真值才报绝对几何误差；不把投影覆盖或点数当成真实精度 |
| 浏览器 | 浏览器、视口、显卡与是否软件渲染；初次加载耗时、旋转/缩放/复位、失败现象；下载并与服务端文件比对哈希 |

现有 `scripts/sample_resources.py` 可用于任务初期至终态的 GPU、COLMAP RSS 与工作区采样。它需要已存在的任务 ID，不会覆盖提交前基线，且 `ps %CPU` 不是瞬时 CPU 使用率；另行采集提交前基线和按间隔计算的 CPU 指标。工作区是周期采样，也要单列输出文件大小。归档到 `docs/gpu-benchmark-evidence/` 或同类证据目录，仅保存脱敏日志、表格、JSON 和必要截图，不纳入原片、数据库、模型或凭据。

每轮记录模板（实际未测填 `未采集`，估算填 `估算` 并链接公式）：

```text
场景 / GPU 数 / 分辨率 / 重复编号：
Git 提交 / COLMAP 版本 / 输入清单 SHA-256：
任务 ID / 产物 ID / 缓存状态 / 并发情况：
提交 / 开始 / 结束 / 终态 / 失败阶段：
排队 / 墙钟 / 逐阶段耗时与日志路径：
资源采样区间、间隔、峰值口径与原始文件：
注册 / 重投影误差 / 点与面 / 贴图面率 / 产物 SHA-256：
同视角照片与截图 / 浏览器检查 / 局限：
```

## 4. GPU 空闲前也能做的验收

- **阶段 7 / E6 失败保护：** 在测试项目先生成并记录旧模型、版本和下载 SHA-256；追加后提交更新，在可控测试环境让发布前失败，确认旧版仍能打开和下载、哈希不变、无错误新版本。再测排队或运行中上传的图片不应算作已参与本次重建；版本归因应比较冻结输入清单，不按上传时间推断。若评价追加照片的质量收益，前后固定同卡数、同分辨率。
- **阶段 8 原型：** 补上网页工具栏入口和“区域提取”标签，用真实模型测试拖拽、旋转后框选、拖出画布/取消、任务入队与结果下载；确认源文件哈希不变、选区不过度选中背面。E7 的局部更新实验仍未完成：裁剪或对比两次全量重建都不能证明局部融合。
- **E8 多任务调度：** 用隔离 Redis/RQ 和两个测试项目，分别记录单任务基准与两任务排队；验证排队等待、领取顺序、是否重叠、API 响应、取消/失败后下一任务是否继续。用 mock/轻量任务可先测行为，但要标明不代表真实 GPU 吞吐。
- **阶段 9 答辩前彩排：** 按图文用户手册由组员实际走一遍，核对用户隔离、上传限制、任务日志、加载/交互和下载。另做断网彩排，确认备用模型、演示视频、报告和 PPT 不依赖临时目录或现场重建。
