# Bridge 完整冷跑：基线与组合提速

## 目的与对照条件

把已经能目测的短测点云、融合点云和贴图档位实验推进到完整照片贴图 GLB。以 **C00 与 C01 的新实测** 判断收益；旧 [B00 和分项实验](../版本管理.md)仅供参考。

| 版本 | PatchMatch 迭代 | 融合线程 | 贴图初始档位 |
| --- | ---: | ---: | --- |
| C00 · Bridge 完整基线 | 5 | `-1`（COLMAP 自动） | 0.5，超限则降至 0.25 / 0.125 |
| C01 · Bridge 组合提速 | 3 | 16 | 0.125，仍严格检查图集上限 |

固定 Bridge 100 张原片及顺序、双 A800、CUDA COLMAP 3.13.0、CPU 贴图器 4.2.1、稠密长边 3000 px、standard / exhaustive、几何一致性、Poisson depth 10。原片按 [SHA-256 清单](../phase2-evidence/bridge100.sha256) 校验。两组分别上传、创建新项目和新任务，串行运行，绝不复用上组检查点。每组仅一次，不能把组合收益单独归给一个改动，也不能从设备级采样反推峰值或通信瓶颈。

## 证据和验收标准

- 任务状态、耗时与产物以独立服务的数据库、阶段日志和实际文件为准。墙钟从 Worker 开始到成功发布；排队时间单列，不以客户端轮询时钟代替。资源采样从任务进入队列到终态，报告设备利用率采样、显存、COLMAP RSS 和工作区大小。`ps %CPU` 为进程生涯平均值，不是瞬时 CPU 利用率。
- 必须通过 `scripts/e2e_test.py --require-photo`：缺少照片贴图或贴图阶段未完成时，不作为完整结果发布；比对查看和下载文件，并在归档前核验实际文件的 SHA-256。
- 使用 `scripts/collect_combined_benchmark.py` 核对两组原片哈希、注册照片和实际参数，选取相同的 12 个源照片，在固定评测分辨率、点半径和膨胀口径下比较点云投影覆盖、网格覆盖及点支撑，并输出照片叠图。两组各使用自己的相机位姿；投影指标不处理完整遮挡关系，不是绝对几何精度。最终仍须人工查看照片 GLB，重点对比窗框、立面、屋檐及薄结构。
- 两组成功并取得证据后，先在线备份独立验收库，再以 `--append` 导入 [优化实验验收项目](../版本管理.md)，不覆盖原有编号和文件。不切换 18082，也不修改生产默认值。

## 实测结果

C00 的初始 HTTP 轮询断开，Worker 和采样持续运行；重连同一个任务 ID 后校验通过，未恢复或重跑计算，也未复用阶段。**墙钟按数据库起止时间**，不是重连后的 3754.5 秒。C01 偶遇连接重置后自动重试，未重复提交。
